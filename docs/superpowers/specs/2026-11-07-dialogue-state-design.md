# 短期会话状态与连续追问理解设计

日期：2026-11-07（Asia/Singapore）

状态：本落盘设计已于 2026-11-07 获用户确认；实施计划另文编写，尚未开始业务实现。

范围：设计文档，不包含业务代码修改、数据库执行或工作流发布。

## 1. 目标与已确认选择

采用「统一问题理解层 + 结构化会话状态 + 完整问题贯穿检索和生成」方案，同时覆盖本地普通聊天和患者端。近期原文及自然语言摘要继续保留，作为语义状态的补充和重建依据。

必须正确处理以下连续三轮：

| 原始问题 | 主题变化 | 意图变化 | 独立完整问题 |
|---|---|---|---|
| 高血压在日常生活中需要注意什么？ | 建立高血压主题 | 日常注意事项 | 高血压在日常生活中需要注意什么？ |
| 糖尿病呢？ | 切换为糖尿病 | 继承日常注意事项 | 糖尿病在日常生活中需要注意什么？ |
| 那它是由什么引起的？ | 保留糖尿病 | 切换为病因 | 糖尿病是由什么引起的？ |

非目标：诊断用户疾病、改造长期画像、自动迁移患者历史到本地 SQLite、跨患者或跨会话召回、重做向量库、重构身份系统、增加新的模型供应商。

## 2. 当前实现与故障依据

以下事实来自当前工作区代码，不代表已观测到真实模型在每次调用中均失败：

1. `short_term.py` 仅提供近期问答和自由文本摘要，没有当前主题、意图、待澄清问题等显式状态。
2. `workflow/nodes/question.py` 的省略词集合使用完整字符串匹配。「糖尿病呢？」被判为 `direct/self_contained`，而不是上下文补全。
3. `medical-answer.v6.json` 的初始检索使用改写结果，但重排和回答规划使用原问题。生成也收到原问题，必须再次自行消解。
4. `PatientService.ask()` 调用 `ChatClient.answer(question)`；客户端向 `/answers` 仅发送问题、top_k 和 `memory: false`，没有患者近期问答。
5. `summarize.py` 用全局自增 turn ID 减去窗口轮数推算摘要边界。ID 间隔并不等于本会话实际轮次，应按会话内有序记录计算。
6. 现有短期记忆及患者客户端测试共 65 项通过，但不覆盖所述三轮语义理解的真实模型质量。

因此本改动需要同时修复入口、语义契约和消费链路，不能只调整提示词或扩大窗口。

## 3. 备选方案与取舍

| 方案 | 优点 | 局限 | 结论 |
|---|---|---|---|
| 只补规则和上下文接线 | 改动最少、额外延迟小 | 多对象指代和话题切换仍不稳定，缺少可追踪状态 | 作为回归用例来源，不作为最终方案 |
| 结构化解析与状态 | 主题、意图和引用对象可检查；两个入口共享算法 | 增加状态存储和解析失败处理，部分直答问题增加模型调用 | 采用 |
| 每轮发送全部历史 | 实现表面简单 | 成本随历史增长，仍存在指代歧义和历史污染 | 不采用 |

## 4. 总体架构

```text
用户原问题
  → 入口鉴权 / 会话归属校验
  → 一致性快照：状态 + 最近已完成问答 + 摘要 + 内容版本
  → QuestionResolver：主题、意图、指代、完整问题
       ├─ resolved：检索 → 重排 → 检索纠错 → 规划 → 生成 → 引用校验
       └─ clarification：固定澄清模板，不执行医学检索和生成
  → 再鉴权 / 内容版本比较
  → 同一事务提交问答、会话状态与新版本
```

普通聊天和患者端共享纯解析组件与工作流契约，不共享历史数据库、用户画像或患者授权对象。

本地问答服务收到患者上下文时只在本次运行内使用，不写患者历史、长期记忆、会话向量或持久化 run 记录，也不把含患者内容的运行结果留在共享 `RagService.runs` 缓存供 `/runs/{id}` 读取。普通本地聊天原有持久化不受影响。

## 5. 数据模型

### 5.1 ConversationState：持久化语义状态

```json
{
  "schema_version": 1,
  "revision": 2,
  "through_turn_id": "turn-2",
  "active_topic": {
    "name": "糖尿病",
    "type": "disease",
    "source_turn_id": "turn-2",
    "source_role": "user"
  },
  "active_intent": "daily_precautions",
  "active_intent_text": "在日常生活中需要注意什么",
  "last_resolved_question": "糖尿病在日常生活中需要注意什么？",
  "pending_clarification": null
}
```

- `schema_version` 是格式版本，初版固定 1。
- `revision` 是应用维护的语义状态版本，不由模型指定。
- `through_turn_id` 是权威存储中最近已完成问答的边界标记；使用字符串兼容 SQLite ID 和患者端标记，不对 ID 做轮次算术。
- `active_topic` 可为空；类型限定为 `disease / medication / procedure / lifestyle / other`。
- `active_intent` 限定为 `daily_precautions / etiology / symptoms / diagnosis / treatment / medication_usage / prevention / prognosis / comparison / other`。
- `active_intent_text` 保留具体任务限定，避免仅凭宽泛枚举继承错误问题。
- 多对象比较不能压缩成任意一个单主题。保留完整问题，单主题设空；之后的模糊单数追问需要消歧。
- `active_topic` 表示讨论对象，不表示用户患病，也不自动写入健康画像。
- 用户明确切换对象优先于助手回答中的附带实体。助手提到的对象只有在当前用户明确引用且唯一时才可参与消解，必须标注 `source_role: assistant`，不能变成已核实医学事实。

### 5.2 Resolution：本轮问题理解结果

```json
{
  "original_question": "那它是由什么引起的？",
  "resolved_question": "糖尿病是由什么引起的？",
  "relation": "follow_up",
  "intent": "etiology",
  "intent_text": "由什么引起",
  "topic": {
    "name": "糖尿病",
    "type": "disease",
    "source_turn_id": "turn-2",
    "source_role": "user"
  },
  "references": [
    {"expression": "它", "entity": "糖尿病", "source_turn_id": "turn-2"}
  ],
  "status": "resolved",
  "clarification": null
}
```

- `relation` 限定为 `standalone / topic_switch / follow_up / clarification_reply`。
- `status` 限定为 `resolved / clarification`，不能用模型自报的置信度直接授权继续作答。
- `resolved` 必须提供非空完整问题；`clarification` 不得向检索阶段提供可执行 query。
- `original_question` 由应用原样赋值，模型输出不能覆盖。
- 解析器只返回候选状态；存储版本、提交边界和是否落库由入口运行时决定。
- 原始问题、完整问题、检索 query 分开保存，不能用其中一个反复覆盖其他字段。

### 5.3 PendingClarification：澄清后的续接

未能确定对象时，保存有来源的候选对象、已明确的意图、原始问题及来源轮次，不改变已确定的主题。最多保存一个待澄清项，候选对象最多 3 个。

例如「高血压和糖尿病…… → 它是什么引起的？ → 糖尿病」：最后一轮必须恢复待澄清的病因意图，而不是把「糖尿病」当成一个全新介绍请求。

用户给出新的完整问题时，清除旧待澄清项，不继续纠缠旧问题。解析故障只能生成通用补全提示时，不凭空建立具体候选对象或意图。

### 5.4 校验与预算

- 使用 Pydantic 严格模型，禁止额外字段，校验枚举、类型、长度和跨字段约束。
- 保持现有输入上限：普通聊天 20000 字符，患者端 16000 字符；完整问题最多 20000 字符。不对长完整问题套用旧的 256 字符改写上限。
- 实体名称最多 100 字符；来源及边界标记最多 128 字符；具体意图最多 200 字符。
- 单个会话状态序列化后最多 8 KiB（UTF-8），超限视为不可用候选，不截断成非法 JSON。
- 近期窗口沿用最多 3 轮、问题 200 字符、回答 400 字符、合计 1200 字符；摘要最多 800 字符。结构化状态独立于该窗口预算。
- 历史对象必须来自快照中的有来源状态或实际文本；拒绝不存在的来源轮次、未来轮次、无文本依据的新对象及对象类型混淆。
- 模型输出可通过结构校验仍不等于语义正确，必须另做真实模型评测。

## 6. 解析与状态转换规则

新增 `QuestionResolver.resolve(question, snapshot)`；`snapshot` 是不可变的状态、近期问答、摘要和内容版本组合。

规则优先级：

1. 当前用户明确对象覆盖旧主题，当前明确意图覆盖旧意图。
2. 「新对象 + 呢」表示对象切换并继承上一个可继承的具体意图。
3. 代词追问保留唯一可确定的对象，但允许改变意图。
4. 否定、更正和显式换话题优先于简单的最近实体匹配。
5. 缺少对象、存在多个合理对象或继承意图不明时进入澄清。
6. 不能把「讨论糖尿病」转换成「用户患糖尿病」，也不能新增疾病亚型、诊断、剂量或危险因素。

所有轮次进入同一个解析接口。确定性规则只有在能完整产出且满足来源校验时才返回快速结果；不能仅因问题较长就认定不依赖历史。其余情况最多调用一次结构化解析模型，替代旧问题改写调用，不拆成多次分类和改写调用。

解析超时固定为 8 秒，不在该步骤重试。不承诺完整问题一定零额外调用：初版优先保证状态完整和正确性，再依据测量结果扩展快路径。

模型失败时：只有保守规则已独立确认对象、意图完整的问题才可原样继续；带指代、省略、待澄清续接或不确定是否完整的问题一律请求补充，不拿模糊原话检索碰运气。

## 7. 工作流与生成契约

新增 `medical-answer.v7.json`，保留已有 v6 文件。新增 `question.resolve` 节点，负责输出完整问题或澄清结果；其状态更新候选只在本次运行内部传递，不作为证据端口。

| 消费者 | 必须使用的输入 |
|---|---|
| 初始 dense / BM25 / HyDE | `resolved_question` |
| 第一轮重排 | `resolved_question` |
| 检索反馈纠错 | 固定语义问题 `resolved_question`，另行记录检索改写 query |
| 回答规划 | `resolved_question` |
| 最终生成 | 主问题 `resolved_question`，独立附带 `original_question` 及有界上下文 |
| 引用校验 / 证据门控 | 真实资料 evidence，不接收语义状态作为证据 |

纠错只改变检索表达，不改变已消解主题、意图和用户约束。无法验证语义一致时放弃该纠错 query，保留首轮有效结果。检索分数足够高不能替代问题理解成功。

澄清在检索前分支返回固定模板，不调用医学生成器。普通聊天流和非流接口均须能完成该分支，不能等待不存在的引用事件。

新增可选 `answer_type: answer | clarification`，缺失时按 `answer` 解释。澄清使用 `citations: []`、`abstained: false`，仅表达补充问题而非医学结论；证据不足仍使用既有 `abstained` 语义。所有外部 API 继续返回 `{success, data, error}`。

## 8. 两个入口与存储适配

### 8.1 普通本地聊天

- `ChatRuntime` 在一致性读取中装载窗口、摘要、语义状态和内容版本。
- SQLite 新增 `conversation_states`，以 `conversation_id` 为主键，保存状态 JSON、状态版本、内容版本及已完成边界。
- 旧会话首次使用时从本会话近期问答与摘要重建，不要求批量调用模型回填。
- 同一会话已有其他处理中的请求时，返回现有 `REQUEST_IN_PROGRESS`；现有 request ID 重放仍按原幂等机制处理。
- 原始结果、状态、请求结果和既有 outbox 在最终事务中协调保存；生成失败不推进语义主题。
- 导入、删除和追加历史等所有会影响上下文的写入路径必须更新或失效化内容版本；删除会话显式清理派生状态，不依赖未启用的外键级联。

### 8.2 患者入口

- 在 `PatientService` 的授权事务中校验租户、患者、会话归属及当前有效同意，读取 PostgreSQL 状态及近期已完成问答。
- 近期消息按 `ordinal` 排序；只把同一会话内相邻、已提交的 user / assistant 配对当成已完成问答。单独 `append_turn` 的未回答用户消息不伪装成已完成一轮。
- 读取时用会话行的短期共享锁保证状态和窗口一致；模型调用前释放事务。
- `ChatClient.answer` 增加 keyword-only 的有界上下文参数；由后端构造，浏览器不能覆盖。
- `/answers` 增加可选上下文负载并透传至共享解析与工作流。旧的无上下文调用保持兼容；传入上下文不触发本地历史或向量索引读取。带该上下文的调用使用请求级临时运行模式，禁止写入共享运行缓存及可查询诊断记录；该模式由可信后端调用路径决定，不由模型输出决定。
- 患者调用始终 `memory: false`，不连接旧的单用户长期画像。上下文负载不携带鉴权凭据，也不能授予患者数据库访问权。
- 模型服务可返回严格校验后的状态更新候选，患者后端保存；外部患者响应只暴露作答、澄清类型及原有允许字段，不暴露内部状态和完整解析诊断。

### 8.3 PostgreSQL 迁移与最小权限

新增 owner 执行的 `0009_conversation_dialogue_state.sql`，在已有 `medical_rag.conversations` 上增加：

- `dialogue_state jsonb`：可空，只允许 JSON object。
- `dialogue_revision bigint NOT NULL DEFAULT 0`：非负语义提交版本。
- `context_version bigint NOT NULL DEFAULT 0`：非负内容版本，每次内容写入事务递增一次。

继续使用该表既有的租户、患者 RLS，迁移不得关闭 RLS、放宽会话归属或授予表级通配写权限。运行时授权脚本仅增加上述字段的必要 SELECT / UPDATE 权限。

已有 `conversation_scope` 是同时带 `USING` 和 `WITH CHECK` 的 ALL 策略，能够限制新增 UPDATE 操作；保留该策略，不另建更宽的 UPDATE 策略。迁移新增 `BEFORE UPDATE` 的 `SECURITY INVOKER` 触发器，对 `tenant_id / patient_id / conversation_id / title / created_at` 与旧值做 `IS DISTINCT FROM` 比较，任一变化都拒绝，仅允许更新新增状态和版本字段。运行角色只获得新增三列 UPDATE 权限。迁移测试同时验证 RLS、不可变字段、锁定读取和授权，不能把列权限误当成完整身份认证。

迁移只提供文件和操作步骤，不在开发任务中自动对真实患者数据库执行。

## 9. 事务、版本和失败语义

`revision` 和 `context_version` 不由模型控制。完整快照读出后，在模型调用期间不持有数据库锁。

患者提交阶段重新检查当前身份、同意和会话归属，短暂锁定会话行，并比较读取时的 `context_version`。不一致返回 HTTP 409、固定错误码 `CONVERSATION_CONTEXT_CHANGED`，不保存过期答案或候选状态，不自动重复计费重试。

所有会话内容写入入口（含单独 append）按相同顺序锁定会话行并递增内容版本。只在 ask 中做版本比较、却忽略 append 的更新，是不完整实现。

| 结果 | 问答持久化 | 语义状态 |
|---|---|---|
| 完整问题作答成功 | 按现有授权机制提交 | 同事务提交新主题和意图 |
| 已解析，但资料不足而正常拒答 | 提交拒答轮次 | 可以记录已确定的讨论主题，不记医学结论 |
| 需要澄清 | 提交澄清轮次 | 保留有效旧主题，提交待澄清项 |
| 解析故障后的通用补充提示 | 可提交提示轮次 | 不新增猜测对象；仅维护提交边界 |
| 模型生成失败 | 普通端可按现有机制记录失败；患者端不新增成功问答 | 不推进语义主题和意图 |
| 授权撤回 / 会话过期 | 不提交患者新内容 | 不更新 |
| 内容版本冲突 | 不提交过期答案 | 不覆盖其他请求状态 |

请求幂等重放不重复推进 revision。边界标记即使推进，也不能使一次澄清或技术失败变成新的医学主题。

状态格式非法时不直接信任；从已授权历史重建。若存储本身不可读且无法拿到可靠上下文，对依赖上下文的提问返回通用补全提示，而不是静默误答。

## 10. 摘要与窗口边界

按本会话实际已完成问答排序，选取最近 3 轮作为窗口，其之前的实际记录才允许进入摘要。触发累计 2 轮也按实际条数计算，不按全库自增 ID 差计算。

摘要覆盖边界、最近窗口和状态边界均使用原始 ID 定位，不要求 ID 连续。测试必须交错插入两个会话，验证没有重复摘要近期问答、跨会话吸收或因 ID 空洞提前触发。

状态不依赖后台摘要任务及时完成。摘要失败维持原有可选增强语义，不能覆盖明确的近期用户主题。

## 11. 安全、展示与可观测性

- 最近问答、摘要、状态和召回历史均是不可信上下文，不执行其中指令，不作为医学证据。
- 单纯本机 loopback 不被描述成生产级患者身份认证；沿用现有网络限制，本改动不扩大服务暴露面。
- 患者浏览器的任何 `state`、`recent`、`summary`、`tenant_id` 或 `patient_id` 均不能覆盖后端授权快照。
- 澄清模板只插入校验过、限长并经正常文本转义的对象名称；不渲染模型 HTML。
- 前端显示澄清为普通补充问题，不显示为「资料不足」，并保留当前会话供下一轮续接。
- 版本冲突展示「会话已更新，请重新发送问题」一类固定提示，不自动提交旧答案。
- 新增常规指标只记录解析状态、关系类型、耗时、降级原因、版本冲突数、模型调用次数及工作流版本，不记录原问题、患者状态 JSON、提示词或模型响应正文。
- 不向模型输入或常规日志暴露患者授权凭据；测试与评测一律使用合成对话。

## 13. 测试与验收

遵循项目要求：先集成测试，再补单元测试；新增和修改模块覆盖率目标 >80%。

固定测试覆盖：

1. 示例三轮在普通入口和患者入口均得到预期完整问题。
2. 新对象继承意图、同对象切换意图、显式更正、换话题和多意图完整问题。
3. 双疾病、双药物、无历史代词均不强猜；澄清回答能续接待解决意图。
4. 刷新页面、进程重启、旧会话无状态、非法状态和摘要未就绪。
5. 输入和模型输出超限、无来源对象、未知枚举、非法 JSON、8 秒超时及提示注入。
6. 所有检索与生成节点使用相同语义问题；语义状态不进入 evidence。
7. 两会话交错 ID 的摘要边界，以及预算裁剪后状态仍可用。
8. 不同患者、不同租户和不同会话的历史与状态隔离；浏览器伪造上下文无效。
9. 并发 ask、ask 与 append 交错、授权撤回、会话过期和 request 重放。
10. 澄清、正常拒答、技术失败、冲突和流式终止均保持 API 契约。
11. 受限 PostgreSQL 运行角色权限足够，但不能更新归属字段、越权行或执行迁移。
12. 关闭新功能时旧调用和旧工作流仍可运行，开关关闭不能被最高 published 版本绕过。

真实模型评测集固定 40 组、每组 3–6 轮，其中 10 组包含必须澄清的歧义，全部使用合成数据。评测标注主题、意图、必要约束、允许的完整问题语义及是否应澄清，不要求生成问题逐字一致。

发布门槛：示例回归及安全、故障、并发测试全部通过；真实模型评测主题和意图正确率分别达到 95%，10 组必澄清样例全部澄清，且不得出现跨患者上下文。阈值是待验证的验收目标，不是当前已达成的效果。

记录原 v6 与新方案在同一配置下的端到端及解析阶段 p50 / p95 延迟、模型调用次数和 token 用量。解析请求自身受 8 秒上限约束，不将网络和其他模型耗时描述成整体 8 秒承诺。真实模型调用需要在执行阶段明确费用与授权，不由普通单元测试隐式触发。
