# 用户问题扩展工作流设计

## 目标与范围

为公开医疗资料 RAG 增加四个可复用的用户问题处理节点：问题重写、复杂问题分解、假设性回答（HyDE）和抽象问题（step-back）。发布独立的可选问答工作流 `medical-answer-expanded`，保留已有 `medical-answer`、`medical-search` 及 `/answers` 默认行为。新流程从现有工作流运行接口调用，并在节点库及编辑器中可见。

四个节点处理用户的原始问题，不检查检索结果。“抽象问题”每次生成更上位的问题，不以检索失败为触发条件。该流程不改变资料上传、索引、默认检索和默认问答流程。

## 方案比较与选择

1. **并列扩展后融合（选用）**：四个转换独立接收原问题，再汇总检索、统一重排。优点是原问题始终保留、各扩展方法互不传播偏差；代价是更多 Qwen 调用与检索开销。
2. 串行转换：按重写、分解、HyDE、抽象问题依次处理。图较简单，但前一步错误会污染后续步骤，且难以保留独立候选。
3. 动态选择转换：先判别复杂度再选择少数节点。可节约开销，但现有工作流引擎是固定 DAG，条件执行需要额外机制。

这里“并列”是独立的数据分支；现有引擎按确定的拓扑顺序执行节点，本次不承诺真正并发的模型请求。

## 节点接口与职责

四个新节点使用现有 Qwen 传输接口，输入均为 `question: string` 和 `provider: string`，输出如下；节点提示词将用户输入视为数据，不执行用户输入中要求改变节点职责的指令。

| 节点类型 | 输出端口 | 职责 |
| --- | --- | --- |
| `question.rewrite` | `question: string` | 保留原意，补全检索所需的明确措辞；不引入医学事实。 |
| `question.decompose` | `questions: string_list` | 把确有多个子目标的问题拆为最多 3 个独立可检索子问题；简单问题输出原问题。 |
| `question.hyde` | `hypothetical: string` | 生成简短、明确标记为未验证的模拟回答文本，仅作向量查询。 |
| `question.stepback` | `question: string` | 生成一个更上位、但仍与原问题主题相关的抽象问题。 |

转换输出要求为结构化 JSON，解析后校验类型、非空、长度和数量。格式无效、空内容或重复内容时使用原问题代替该分支；去除空白差异造成的重复，限制每条查询和模拟回答的长度。真实模型调用失败（包括认证、限流和服务不可用）沿用现有安全错误路径，令新工作流失败，不把它冒充证据不足。密钥不进入工作流 JSON、追踪记录或用户响应。

新增 `question.bundle` 汇总节点接受原问题、重写问题、最多三个子问题、抽象问题及模拟回答，产出有来源标记的 `query_plan`。原问题必定排在第一位；其余文本去重，最多形成 6 条问题类检索文本与 1 条模拟回答。模拟回答只标记为向量查询，不作为事实证据。新增 `retrieval.expanded` 节点接受 `query_plan`，对每条问题类文本执行向量和 BM25 检索，对模拟回答只执行向量检索；各次检索使用现有配置的候选数上限，并以块 ID 去重、RRF 合并，输出 `evidence_list`。节点不把模拟回答文本塞入 Evidence。新增类型只在相关端口间传递，不改变已有节点接口。

## 工作流数据流与安全边界

`query.input` 的原问题和 provider 分别连到四个转换节点；原问题及四个输出进入 `question.bundle`，再由 `retrieval.expanded` 产出候选证据。候选证据进入既有 `retrieval.rerank`，其 question 端口仍使用原问题，top_k 仍来自 `query.input`。其后保持 `evidence.gate` → `generation.llm` → `citation.validate` → `answer.output`，回答生成的 question 端口仍使用原问题。既有问答安全校验要求 gate 的证据来自 rerank、生成证据来自 gate、答案来自引用校验；新图须满足这些约束。

四个转换结果只能扩大候选召回，不能成为回答内容、引用来源或医学事实。证据为空或不满足门槛时继续使用现有固定拒答；有效引用必须指向本次检索到的真实资料块。发布 `workflows/medical-answer-expanded.v1.json`，不替换或改写现有默认工作流。通过 `/workflows/medical-answer-expanded/runs` 调用；现有 `/answers` 和 `/search` 不切换工作流。

## 验证与边界

自动化测试用伪 Qwen 传输和内存检索对象，不调用收费 API。覆盖每个节点的正常结构化输出、简单问题、非法 JSON、空值、超长文本、子问题上限、模型调用失败；覆盖汇总去重和原问题优先、HyDE 只调用向量检索、跨查询块 ID 融合，以及新图的发布校验和端到端运行。回归测试确认旧图输出、拒答、引用校验及 `/answers` 默认绑定不变。按项目开发命令运行 Python 测试与静态检查；涉及前端节点库展示时运行前端测试、lint 和 build。真实 Qwen/Milvus 表现另以受控环境验证，自动化通过不等于医学正确性已验证。

每次运行至多尝试 6 条问题类文本和 1 条 HyDE 文本；当前同步模型传输及顺序 DAG 执行会增加延迟和调用量。这是独立可选流程的明确代价，不在本次增加条件调度、并发执行、新页面或自动切换默认流程。
