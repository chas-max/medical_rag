# 对话界面工作流选择设计

## 目标与范围

用户在医疗问答页直接选择已发布、可完成一次从问题输入到检索、证据处理、模型生成及答案输出的工作流，并在同一页面继续提问。不能生成完整答案的检索和文档入库工作流不出现在面向对话的选择列表，但其定义、运行接口及支撑 `/search`、`/documents` 的功能保持不变。

## 交互

- 在问答页的输入区上方常显工作流选择器，列出符合条件的已发布工作流；默认选中 `medical-answer`，若该项不可用则选第一项。
- 切换选择仅影响之后发送的问题，不迁移或删除已有对话与回答；当前页面保持在问答页。发送前明确显示当前工作流。
- 请求使用当前选择的工作流 ID，通过现有 `POST /workflows/{id}/runs` 执行；结果与错误仍显示在所属对话中，保留现有证据数设置和引用展示。
- 工作流列表加载失败或没有可用回答流程时，不以假的默认选项允许发送；显示可理解的错误或空态。
- 编辑器仍可从问答页打开所选工作流以编辑、校验和发布。移除编辑器中的“测试问题／运行已发布版”入口及内嵌回答，但保留校验结果；不把切换工作流误当作进入对话。

## 筛选与架构

`GET /workflows` 继续返回全部已发布流程，供其他能力使用。前端以独立的可测试筛选函数识别回答流程：从 `query.input` 能沿有向连线到检索节点，检索节点沿连线能到 `generation.llm`，生成节点沿连线能到 `answer.output`。同时必须存在 `evidence.gate` 和 `citation.validate` 且分别位于检索到生成、生成到输出的路径上。这样内置 `medical-answer` 和 `medical-answer-expanded` 可选，`medical-search` 与 `document-ingestion` 不可选；未来符合相同合同的已发布流程可自动出现。后端现有发布校验和运行校验仍为最终权威，不靠前端筛选提供安全保证。

对话页在首次获取列表后设置有效选择，发送时捕获所选 ID；加载期间禁用发送以避免错用默认 ID。工作流切换不修改本地历史消息结构，旧对话继续可读。编辑器的工作流跳转只用于编辑；问答发起统一在问答页进行。

## 错误与验证

增加针对筛选函数及问答页的测试，覆盖两种回答流程可选、非回答流程不可选、切换后从问答页以新 ID 发起请求、无可用流程不发送、失败/空态，以及旧对话兼容性。编辑器测试验证测试提问入口已移除而校验仍可用。运行前端测试、类型/静态检查与构建，以及相关后端工作流测试；手动核对问答页切换流程。只改本需求所涉及文件，保留工作区其他未提交修改。
